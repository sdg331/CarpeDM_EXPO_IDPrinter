# 프론트엔드 1차 구현 · 2026-09-15

## 범위

`sdg331/CarpeDM_EXPO_IDPrinter`의 초기 README 위에 인수인계 문서와 기존 Raspberry Pi 코드/자산을 가져왔습니다. 새 프론트엔드를 명세에 따라 구현했으며, NFC·리포트·AI B의 실제 백엔드 구현은 이번 범위에 포함하지 않습니다.

Figma 파일은 제공되지 않았습니다. `DESIGN.md`의 높은 명암 대비·터치 우선·800×1280 원칙을 적용한 코드 기반 시안입니다. 사용자 피드백에 따라 현재는 화이트·블루 톤으로 구성했으며, 최종 브랜드 컬러 확정은 별도입니다.

## 구현

SCR-01~20과 SCR-90 유휴 경고에 대응하는 화면을 제공합니다. A/B 선택은 촬영 전, 팀은 확정된 6개이며 팀 소개/업무/키워드는 원문을 사용합니다.

- 이름: 앞뒤 공백 제거, 유니코드 코드포인트 1~10자, IME 조합 중 제출 금지.
- 카메라: 실제 스트림·감지 API, 얼굴 없음/다중 인원/권한 오류. 현재 API에 없는 자세 품질·바운딩 박스를 만들어내지 않음.
- AI A: 실제 매칭 API 응답 검증. 원시 점수 미노출, 랜덤 폴백 없음.
- AI B: 화면과 고정 샘플만 제공. 사용자 사진을 외부 서비스로 보내지 않음.
- NFC: 대기/감지/쓰기/검증/실패 화면, 검증 완료와 서버 세션 ID가 있어야 출력 진입.
- 출력: 배지/리포트에 서로 다른 작업 ID. 동작 중 재제출/뒤로 이동 차단.
- 오류: 안전한 재시도 시 입력/결과 유지. 결과 불명 상태는 재출력·홈 복귀·유휴 초기화를 막고 스태프 확인 안내를 유지.
- 초기화: 메모리 상태·사진 Blob 참조·카메라 스트림·작업 ID·리포트 제거. 이전 요청 응답 무효화.
- 완료 후 15초 초기화. 유휴 45초 경고/60초 초기화. 진행 중 작업은 유휴 초기화에서 제외하고 25초 작업 타임아웃 적용.
- 폰트: 기존 배지 렌더러에 Windows 맑은 고딕 검색 경로를 추가. 실제 Pi/Mac 경로는 유지.

## 명시적 화면 체험

`?demo=1`에서만 활성화합니다. 카메라·NFC·프린터에 접근하지 않으며 화면 상단과 결과 화면에 예시임을 표시합니다. 이름/팀은 현재 입력값, AI 결과는 고정 샘플입니다. 퇴근에서는 이전 관람객 정보를 재사용하지 않고 김미래/디자인팀의 별도 고정 예시를 조회합니다. 날짜·피드백도 예시로 표시합니다.

상단 `체험 설정`에서 정상, 지연, 카메라 오류, 얼굴 없음, 다중 인원, AI 오류/시간 초과, NFC 오류/시간 초과, 프린터 오류, 미등록 카드, 기록 없음, 서비스 점검을 선택합니다. 재시도 시나리오는 첫 요청 실패 후 다음 명시적 요청에 성공하도록 고정되어 있습니다.

## 실제 연결할 계약

`frontend/js/live-integrations.js`의 메서드를 구현해 `liveIntegrations` 객체로 내보냅니다. 기존 REST 경로와 신규 제안 경로를 혼동하지 않도록 미구현 메서드는 명시적으로 중단합니다.

| 메서드 | 성공 시 필수 반환값 |
| --- | --- |
| `generateProfile(frame, context)` | `{ kind: 'B', image: '같은 출처 이미지 경로' }` |
| `registerNfc(profile, context)` | `{ status: 'verified', sessionId: '서버 발급 ID' }` |
| `issueBadge(sessionId, context)` | `{ status: 'success' }` — 실제 완료 확인 후 |
| `resolveCheckout(context)` | `{ sessionId, name, teamId }` |
| `getMirrorTingReport(sessionId, context)` | `{ status: 'available', sessionId, reportId, scenario, summary, ... }` 또는 `{ status: 'not_found' }` |
| `printReport(report, context)` | `{ status: 'success' }` — 실제 완료 확인 후 |

`context`에는 `signal`, `operationId`, `onStatus`가 있습니다. UI 요청 ID는 중복 의도를 식별하는 값이며 사원 번호가 아닙니다. 서버는 같은 `operationId`의 재요청을 중복 실행하지 않고 기존 작업 결과를 반환해야 합니다. 출력 완료/카드 쓰기 결과를 모르면 `UNKNOWN_OUTCOME`으로 중단하고 운영자가 작업을 확인해야 합니다. 현재 레거시 `/api/issue`는 이 보장을 제공하지 않으므로 자동으로 연결하지 않았습니다.

예상되는 오류는 `api-client.js`의 `KioskError(code, retryable)`로 변환합니다. `retryable: true`는 서버 측 중복 방지가 확보되고 재시도가 안전할 때만 사용합니다. 진행 상태는 백엔드가 관측한 경우에만 `onStatus`로 전달하며, 숫자 진행률은 표시하지 않습니다.
