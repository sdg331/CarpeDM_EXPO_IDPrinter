> 작성 2026-07-28. 목업(`kiosk-mockup.html`)을 실제로 가동되는 키오스크로 만드는 계획.

## 0. 결론

가동 가능하다. 소프트웨어 난이도는 높지 않다 — YuNet·SFace는 둘 다 OpenCV에 내장돼 있고
외부 API도 인터넷도 필요 없다. **진짜 위험은 코드가 아니라 매칭 품질과 파이 이관 두 곳에 있고,
계획은 그 둘을 앞으로 당기는 데 초점을 맞춘다.**

권장: **8/1 중간심사 데모는 맥으로, 파이 5는 병행 브링업 후 본전시에 이관.**
4일 안에 파이 셋업 + 프린터 + 매칭 검증을 동시에 끝내는 건 실패 확률이 높다.
코드는 처음부터 맥/파이 양쪽에서 도는 구조로 짜서 이관 비용을 없앤다.

## 2. 반드시 먼저 짚을 위험 3가지

### 2.1 "유사도 82%"는 그대로 띄우면 안 된다 ★설계 결정

SFace는 **동일인 검증** 모델이라 원시 코사인을 그대로 백분율로 보여줄 수 없다.
0.18을 "유사도 82%"로 표시하면 근거 없는 숫자가 되고, 심사위원이 "그 82%가
무슨 뜻이죠?"라고 물으면 답할 게 없다.

> **1단계 실측으로 정정** — 계획 초안에서는 원시 코사인이 0.0~0.25에 몰릴 것으로
> 봤으나, 캐릭터끼리는 **0.27~0.81**로 훨씬 높게 나왔다. 8종이 같은 프롬프트
> 템플릿으로 생성돼 공통 성분이 크기 때문이다(§7). 방향은 같지만 원인이 다르므로
> 정규화 방식도 §7의 도메인 보정을 거친 뒤에 적용한다.

**해결 — 상대 분포로 정직하게 바꾼다.**
8종 점수를 정규화해 합이 100이 되게 하고, 문구를 "유사도"가 아니라
**"8종 중 이 캐릭터에 가장 가깝습니다"**로 바꾼다. 이건 문자 그대로 참이라 캘리브레이션이
필요 없고, 심사 질문에도 그대로 답할 수 있다.
원시 코사인 값은 진단 모드(§6.3)에서만 노출한다.

### 2.2 캐릭터가 8장뿐 — 평균 프로토타입 벡터가 없다

`character-prompts.md`가 스스로 지적한 문제다. 1장짜리 프로토타입은 뾰족해서
매칭이 불안정하다. 다만 72장 생성은 시간이 크니 **1단계 게이트 결과를 보고
필요한 캐릭터만** 만든다. 8×8 행렬이 충분히 벌어져 있으면 안 만들어도 될 수 있다.

### 2.3 개발은 맥, 배포는 파이 — 이관을 마지막 날로 미루면 터진다

파이 5에서 새로 생기는 문제들: aarch64 OpenCV 휠, USB 카메라 V4L2 백엔드,
디스플레이 세로 회전, ESC/POS USB 권한(udev), 오프라인 모델 캐시.
전부 개별로는 사소하지만 마지막 날에 몰리면 치명적이다.
→ **3단계가 끝나는 즉시 파이에서 한 번 돌려본다.** 완성 대기 금지.

## 4. 단계별 계획

### 0단계 — 자산 정리 · 환경 (30분)

- `assets/characters/` 로 8장 이동, `char_01.png` ~ `char_08.png`로 정규화
- Python 3.12 venv + `opencv-python`, `fastapi`, `uvicorn`, `pillow`, `numpy`
- YuNet · SFace 모델 `models/`에 캐시
- 프로젝트 골격: `backend/`, `frontend/`, `assets/`, `scripts/`, `models/`

### 1단계 — 매칭 검증 ★게이트 (2~3시간)

**UI를 건드리기 전에 이것부터.** 여기서 막히면 이후 단계가 전부 무의미하다.

- `scripts/build_prototypes.py` — 8종 임베딩 추출 → `prototypes.npz`
- `scripts/similarity_matrix.py` — 8×8 코사인 행렬 출력
- `scripts/distribution_test.py` — 팀원 얼굴 사진으로 매칭 분포 확인

**통과 기준**
- 8×8 비대각 최대값이 지나치게 높은 쌍이 없을 것 → 있으면 그 캐릭터 변형 이미지 추가(§2.2)
- 특정 캐릭터로 쏠리지 않을 것 → 쏠리면 소프트 게이트 가중치 α 조정
- 여기서 나온 실측 분포로 §2.1의 정규화 파라미터를 확정한다

> `character-prompts.md`는 분포 테스트 최소 40명을 요구한다. 8/1 데모까지는
> 팀원 규모(10명 내외)로 방향만 잡고, 본전시 전에 40명을 채운다.

### 2단계 — 백엔드 (3~4시간)

```
POST /api/match    JPEG → { scores[8], top, raw_cosine[8] }
POST /api/issue    { name, dept, char_id } → 배지 렌더 + 출력
GET  /api/health   { camera, printer, models } — 운영 점검용
```

- 얼굴 미검출 · 다중 얼굴 · 저조도 각각의 오류 응답과 화면 문구
- 출력 계층 추상화: `screen` / `escpos` / `cups` 3개 백엔드, 환경변수 전환

### 3단계 — 프론트 연결 (2~3시간)

- `getUserMedia` 프리뷰 + YuNet 얼굴 박스(저해상도, 몇 fps)
- SVG 자리표시 → 실사 `<img>` 교체 (`portrait()` 함수 대체)
- `startAnalyze()`의 난수 제거 → 실제 API 호출
- §2.1에 따라 결과 화면 문구·표시 방식 변경
- **백엔드 장애 시 목업 모드 자동 폴백** — 시연 중 화면이 멈추는 것보다 낫다

> 여기까지가 **8/1 중간심사 데모 범위** (맥에서 구동, 출력은 화면으로 대체)

### 4단계 — 파이 5 이관 (반나절)

- 라즈베리파이 OS 64-bit, Python 3.12 venv, aarch64 OpenCV 휠
- USB 웹캠 V4L2 확인, 디스플레이 세로 회전(800×1280)
- Chromium 키오스크 모드 — LivingLab `setup-pi-kiosk.sh` 재활용
- systemd 유닛으로 백엔드 자동 기동
- **SFace 실측 지연 측정** — 400ms 넘으면 입력 해상도를 낮춘다

### 5단계 — 감열 출력 (2~3시간)

- 80mm 감열지 = 인쇄 폭 72mm = **576 도트** (203dpi 기준)
- 배지 이미지 **576 × 808 px** (72 × 101mm) — 목업의 384×540 비율과 일치
- 캐릭터 인쇄용 변환: 그레이스케일 → 대비 강화 → Floyd-Steinberg 디더링
  (`character-prompts.md` §인쇄용 버전. 대비 계수는 실기로 조정)
- `python-escpos` USB 백엔드 + udev 권한 규칙
- 용지 없음 · 헤드 과열 · 연결 끊김 → 화면 폴백 + 운영자 알림

### 6단계 — 전시 운영 (2~3시간)

- 무조작 자동 리셋 (EXPO 본 시스템과 시간 통일 — `docs/plan` 미해결 항목 6번 참고)

## 7. 1단계 게이트 결과 (2026-07-28 실측)

> **최종 결론 (스타일 세트 40장 확보 후)** — 캐릭터 8종을 **교체해야 한다.**
> 원인은 캐릭터 품질이 아니라 **선정 방식**이다. 얼굴 특징 축으로 설계한 8종이
> SFace 임베딩에서 무작위 선정보다 나쁘게 뭉쳤다. 상세는 §7.4.
>
> **→ 교체 완료 (2026-07-28). 잔차 최대 쌍 0.688 → 0.265. §7.5 참고.**

### 판정 — 원시 코사인으로는 실패, 도메인 보정으로 회복 가능

8×8 행렬 최대 쌍이 **0.810**(03–04)이었다. SFace에서 0.36 이상은 통상 동일인으로
취급되는 구간이라, 원시 점수로는 8종 대부분이 서로 구분되지 않는다.

| 쌍 | 코사인 | | 쌍 | 코사인 |
|---|---|---|---|---|
| 03–04 | 0.810 | | 01–02 | 0.717 |
| 04–08 | 0.756 | | 04–07 | 0.717 |
| 05–06 | 0.750 | | 03–07 | 0.650 |

### 원인 — 캐릭터 설계 문제가 아니라 임베딩 도메인 문제

파이프라인 정상성부터 확인했다. 동일 이미지 1.000, 좌우반전 0.951, 밝기 ±25%
0.94~0.97, JPEG 40 0.988 — **엔진은 정상이다.**

진짜 원인은 여기 있었다.

- 8종 임베딩의 **56.2%가 공통 성분**이다 (평균 벡터 노름 0.750)
- 각 캐릭터와 평균 벡터의 코사인이 0.683~0.823

같은 스타일 블록(같은 조명·배경·정장·화각·연령·인종)으로 생성했으니 SFace가
얼굴 구조가 아니라 **생성 스타일**을 주로 보고 있다. `character-prompts.md`가
"스타일을 8장 전부 똑같이 붙이라"고 한 지시는 조명 편차를 막는 데는 옳았지만,
그 대가로 8종을 임베딩 공간의 한 점에 몰아넣었다.

### 처방 — 도메인별 평균 제거

공통 성분을 빼고 다시 보면 분리가 살아난다.

```
비대각 최대   0.810  →  0.480
비대각 평균   0.499  → -0.141
```

더 중요한 건, 남은 구조가 **설계한 2×2×2 큐브 그대로**라는 점이다.

- 01–02 `0.434`, 05–06 `0.480`, 03–04 `0.439` — 같은 축을 공유하는 쌍끼리 양수
- 04–05 `-0.619`, 01–08 `-0.493` — 하관 폭 축이 다른 쌍은 강한 음수

즉 캐릭터 설계 자체는 의도대로 됐고, 공통 성분에 가려져 있었을 뿐이다.

실제 매칭에는 도메인별로 평균을 뺀다.

```
캐릭터:  p'ᵢ = normalize(pᵢ − μ_char)
관람객:  v'  = normalize(v  − μ_real)
점수  =  v' · p'ᵢ
```

각 도메인에서 "평균 얼굴로부터 어느 방향으로 벗어났는가"만 남겨 비교한다.
사람이 말하는 "닮았다"에 훨씬 가깝고, 심사 질문에도 그대로 설명할 수 있다.

### 7.4 스타일 세트 40장 투입 후 — 진짜 원인이 드러났다

독립 표본 40장으로 μ_style을 다시 잡자 도메인 보정의 효과가 **훨씬 작았다.**
자기 평균일 때의 0.480은 −1/(n−1) 착시였고, 실제 잔차 최대 쌍은 **0.714**였다.

그래서 40장을 기준선으로 삼아 "생성 얼굴은 원래 얼마나 붙어 있는가"를 쟀다.

| 잔차 쌍 유사도 | 중앙 | 90% | 최대 |
|---|---|---|---|
| 스타일 40명끼리 (같은 방식으로 만든 서로 다른 40명) | **−0.040** | 0.383 | 0.756 |
| 캐릭터 8종끼리 | **0.184** | 0.632 | 0.714 |

**캐릭터 8종이 생성 얼굴 평균보다 유난히 붙어 있다.** 최대 쌍 0.714는 생성 얼굴
쌍 분포의 상위 0.4%다. 무작위 선정과 비교하면 더 분명하다.

| 8명 선정 방식 | 잔차 최대 쌍 |
|---|---|
| 현재 캐릭터 (특징 축 설계) | **0.714** — 무작위보다 나쁨(하위 11%) |
| 40장 풀에서 무작위 (중앙값) | 0.560 |
| 40장 풀에서 **max-min 선정** | **0.248** |

무작위로 0.36 미만이 나올 확률은 1.8%뿐이다.

**원인** — 세 축 중 둘을 공유하는 쌍이 사실상 같은 벡터가 된다. 03·04는
이목구비 간격만 다른데, **SFace가 이목구비 간격을 거의 인코딩하지 않는다.**
사람 눈에는 다른 얼굴이지만 모델에게는 같은 얼굴이다. 축을 설계해 조합을 채운
방식이 오히려 근접 쌍 4개를 만들어냈다.

**처방 — 설계하지 말고 측정해서 고른다.**
후보 풀을 넉넉히 만들고 임베딩 공간에서 max-min으로 8명을 뽑는다.
`scripts/select_characters.py`가 이 선정과 μ_style 계산(선정 안 된 나머지로)을
함께 처리한다. 프롬프트는 `scripts/style_set_prompts.md`에 있다.

부수 소득으로 스타일 불일치도 해소된다 — 현재 μ_style·μ_char = **0.760**으로,
기존 8종(정장·넥타이)과 스타일 세트(남색 셔츠)의 의상 문구가 어긋나 있었다.
한 배치로 다시 만들면 사라진다.

### 7.5 캐릭터 교체 완료 (2026-07-28)

max-min 선정을 실행했다. **잔차 최대 쌍 0.688 → 0.265.** 게이트 통과다.

| | 교체 전 | 교체 후 |
|---|---|---|
| 잔차 최대 쌍 | 0.688 (05–06) | **0.265** |
| 원시 최대 쌍 | 0.675 | 0.707 |
| μ_style 표본 | 40장 (캐릭터와 별도 배치) | 32장 (선정 안 된 나머지) |
| 무작위 선정 대비 | 하위 11% | **상위 99.2%** |

원시 최대 쌍은 오히려 조금 올랐는데, 이건 문제가 아니라 §7.3의 예측대로다 —
공통 스타일 성분은 어차피 8종 전부에 실리므로 순위를 바꾸지 않는다. 실제 매칭이
쓰는 값은 잔차 쪽이다.

작업 중 세 가지를 같이 고쳤다.

- **크롭 결함** — 시트에서 자를 때 `scale=2.0`이 격자 한 칸(205px)보다 큰 창을
  잡아, 8종 전부에 윗줄 어깨와 칸 번호가 딸려 들어가 있었다(인쇄본에선 검은 띠).
  경계에서 clamp 하느라 3:4가 깨진 것도 한 장 있었다. 격자 간격을 얼굴 중심에서
  추정해 창을 그 안으로 제한하고, 경계에서는 자르는 대신 밀도록 바꿨다.
  좌표를 하드코딩하지 않는다는 원래 설계는 그대로다.
- **그룹 매핑** — `GROUPS`가 `char_01="A"` 식으로 파일명에 박혀 있었다. max-min은
  선정 순서로 번호를 다시 매기므로 교체 즉시 틀린 값이 된다. 선정 시점에
  `assets/characters/groups.json`을 쓰고 `load_groups()`가 읽는다.
- **무작위 기준선** — `select_characters.py`가 서로 다른 두 표본을 교차 곱해서
  중앙값이 1.000으로 나왔다. 한 표본 안의 쌍만 보도록 고쳐 0.541이 됐다(§7.4의 0.560과 일치).

선정 원본 시트는 `assets/sheets/style_sheet_40.png`에 넣었다. 후보 풀은 여기서
언제든 다시 자른다.

### 남은 블로커 — μ_real 을 구할 실제 얼굴 표본

`μ_real`은 실측 말고 구할 방법이 없다. **이 사진들은 검증용이 아니라 엔진의
입력이다.** 캐릭터 교체와 병렬로 진행할 수 있다.

- 방향 판단 **10명**, 확정 **40명**(캐릭터당 5명)
- `scripts/capture_faces.py --label p01` 또는 `data/test_faces/`에 사진 투입
- 표본 확보 후 `scripts/distribution_test.py --save`

### 변형 이미지 판단

**계속 보류.** 변형 이미지는 프로토타입의 뾰족함을 완화하는 처방인데, 문제는
뾰족함이 아니라 8종 선정이었다. max-min으로 다시 고른 뒤 분포 테스트에서
미매칭·쏠림이 남는 캐릭터만 골라 뽑는다.
